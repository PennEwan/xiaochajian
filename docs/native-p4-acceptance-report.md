### 2.1 只有真实 App 才暴露的问题（均已处理）

1. **MSIX 文件系统虚拟化**：Codex App 是 MSIX 包，它拉起的插件进程写 `%LOCALAPPDATA%` 时，会被系统透明重定向到 `…\Packages\OpenAI.Codex_2p2nqsd0c76g0\LocalCache\Local\…`，与包外运行的同一插件看到的不是同一份数据。→ 数据目录改为 Codex 官方的插件数据目录 `~/.codex/plugins/data/codex-native-assist-<市场>`（不受重定向影响）。
2. **插件页开关会直接结束全部实例**，采集者来不及记录“已禁用”。→ 新采集者启动时，若发现“无人值守的空档”内 `config.toml` 被改过，就把该空档视为未授权（授权时段在上一个采集者最后在线时截断，在配置改动时刻重开）；采集者在收到 stdin 关闭等正常退出信号时标记 `stopped`，这样正常退出后的空档仍可补读。在 App 中实测：关闭期间的内容未被补采，打开后的内容正常记录。
3. **实例运行时无法卸载**（exe 被占用、进程当前目录占用插件目录）。→ 改为与官方内置插件相同的 `cmd.exe /d /c bin\launch.cmd` 启动：先把 exe 复制到插件数据目录、把当前目录切走，再运行副本。实测卸载成功。
4. **App 会调用未声明的 `resources/list`、`resources/templates/list`**。→ 返回空列表，避免 Codex 日志中的错误。
5. **插件被禁用期间、授权仍开时的内容会在重新启用后被补采**（内核测试中发现）。→ 检测到禁用即以 `config.toml` 的写入时间截断授权时段；重新启用时从启用时刻开新时段。

### 2.2 其他观察

- `codex plugin add`（重新安装 / 更新）会把**已禁用的插件重新启用**，而 App 插件页的开关显示不会同步刷新。插件更新会推翻用户的禁用选择——数据侧由上面的空档规则兜底，产品侧需注意。
- 插件更新对**新会话立即生效**，无需重启 App；已打开会话继续用旧版本直到 App 重启。
- 测试提示词如果像任务（如「CLI 测试 F1：App 关闭期间用 CLI 发送…」），模型会把它当任务去调查本机（CLI 默认权限下执行了约 30 条只读命令，已逐条核对无写入）。另外，含「记录」字样的提示词会触发任务记录技能，模型会顺手调用只读的 `recording_status`。技能描述可以收窄触发词。
- 用 App 界面批量归档会话被本机权限策略拦下（盲点固定位置可能误归档你自己的会话），所以 App 内“归档会话后实例是否退出”未测。内核层面：`thread/unsubscribe` 和 `thread/archive` 都不会结束实例，实例随内核退出而结束。

## 3. 任务二：采集停止机制

**机制**（`native/assist/src/Consent.cs`、`Collector.cs`、`Store.cs`）：
- 授权（开/关、范围、每段授权时段、版本号）存在共享库 `assist.sqlite3`。开启只能由授权窗口完成；关闭可以通过对话（`pause_recording`）、授权窗口、`assist.exe pause` 或插件页开关。
- 采集者每批写入在一个 `BEGIN IMMEDIATE` 事务里完成，提交前在事务内复核：授权仍开且版本未变、插件未被禁用、偏移未被他人推进。撤销操作也是写事务，两者串行，所以**撤销一旦提交，之后不可能有任何记录写入**。
- 只采集时间戳落在授权时段内、工作目录在授权范围内的内容；关闭期间的内容以后也不会被补读。
- 不依赖用户再发 Prompt：采集者每 2 s 轮询一次，与对话无关。

**实测停止延迟**（撤销提交 → 采集器状态变为 off；数据层面在撤销提交那一刻即停止）：

| 场景 | 次数 | 最小 / 平均 / 最大 | 停止后新增记录 |
|---|---|---|---|
| 内核，空闲 60 s 后 `assist.exe pause` | 15 | 425 / 1,028 / 1,556 ms | 0 |
| 内核，`config/value/write` 禁用插件 | 15 | 495 / 1,242 / 2,007 ms | 0 |
| 内核，空闲 **30 分钟**后撤销 | 1 | 895 ms | 0 |
| App，对话中说「关闭任务记录」 | 1 | 930 ms | 0 |
| App，空闲 **23 分钟**后撤销 | 1 | 1,939 ms | 0 |
| App，插件页关闭开关 | 2 | 实例 ≤2 s 内被 Codex 结束（观察器 2 s 采样） | 0；关闭期间内容重新打开后也未被采集 |

延迟上限约等于轮询间隔（2 s）加一次提交的时间。

## 10. 仍未解决的限制

1. **不是后台常驻**：插件只在有已加载会话时运行。App 启动时的探测实例、每会话一个实例，都是 Codex 的行为，插件无法改变。
2. **补读是尽力而为**：App 被直接结束、插件被开关、启动时写配置，这些情况插件都无法区分，统一按保守规则处理（空档内配置有变即不补读）。代价是 App 非正常退出前最后不到一个轮询间隔（≤2 s）的内容可能不被采集。
3. **卸载不删除插件数据**：Codex 卸载会保留 `~/.codex/plugins/data/codex-native-assist-<市场>`（含已采集的数据库、DPAPI 加密的充值绑定、日志、副本 exe）。插件没有卸载钩子，需在授权窗口中先「删除已记录数据」，或手动删除该目录。
4. **更新会重新启用插件**（`codex plugin add` 的行为），且 App 开关显示不同步。
5. **账号读取冷启动慢**（6–12 s），首次一次 21 s 失败未能复现；窗口在此期间显示“正在读取”。
6. **旧格式**：本机没有真正的旧版 rollout 样本，旧格式只按“未识别并报告”处理，没有做映射。
7. **审批**：「请求批准」模式下首次充值需用户批准一次；「完全访问」模式下不审批。本插件不通过改注解来免除审批。
8. **App 内归档会话**后实例是否退出未测（见 2.2）。
9. 数据库体积约为 rollout 的 2.4 倍（存了完整脱敏正文和来源信息），长期使用需要清理策略。
10. 生产化前仍需：exe 代码签名、真实充值服务地址、后台合规核查（同上一轮）。
11. （2026-10-29 追加）调试期把任务记录改成了默认开启（`plugin-config.json` 的 `debug_recording_default_on`），**发布前必须改回 `false`**。
